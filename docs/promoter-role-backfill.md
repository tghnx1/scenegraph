# Ограниченная классификация организаторов

Постановка заданий после импорта доступна через `PROMOTER_ROLE_QUEUE_ENABLED=true` и по умолчанию выключена. Она не вызывает модель и не влияет на рекомендации. Запускайте обработку только после применения миграций в тестовой среде; production rollout остаётся закрыт до выполнения критериев качества из спецификации.

Идентификаторы в командах — внутренние `events.id`, не RA ID. Срез обязателен, максимум 1000 уникальных событий. Без `--apply` выполняется только чтение; выводятся hash, количество профилей и приблизительный размер текста в токенах (четыре символа на токен; это не учёт токенов провайдера):

```sh
cd backend
python -m app.promoter_role_backfill_cli --event-id 1 --event-id 2
```

Явный запуск с записью создаёт и печатает ID запуска:

```sh
python -m app.promoter_role_backfill_cli --event-id 1 --event-id 2 --apply
python -m app.promoter_role_backfill_cli --resume-run RUN_ID --apply
python -m app.promoter_role_backfill_cli --next-run --apply
python -m app.promoter_role_backfill_cli --status-run RUN_ID
```

Возобновление сохраняет исходную конфигурацию провайдера, endpoint, версии API, модели и усилия reasoning; при её изменении потребуется новый запуск. Ключи в hash не включаются. Завершённые и уже актуальные события повторно не обрабатываются. При исчерпании квоты запуск получает `paused`, а обработанное остаётся в базе. Временная ошибка оставляет до трёх попыток, но каждая новая попытка требует повторного запуска команды; неизвестные системные ошибки не повторяются автоматически. Advisory lock не позволяет одновременно выполнять два таких запуска.

Для Kimi распознаётся и подтверждённый ответ об исчерпании квоты с HTTP 403. Произвольный 403 не считается квотой и завершает задание как системную ошибку. Текст ответа провайдера в состоянии задания не сохраняется.

Для успешно сохранённого результата `promoter_role_backfill_item.input_tokens` и `output_tokens` содержат usage провайдера, когда он доступен, включая повтор ответа с неверной структурой. `NULL` означает, что точный учёт недоступен или вызова модели не было; не следует считать его нулём. При ошибке провайдера до сохранения результата usage частичных попыток пока не учитывается.

`--next-run` обрабатывает одно задание с текущей конфигурацией. `paused` автоматически не выбирается: его возобновляют по ID после устранения причины. Для постоянной обработки есть отдельный `promoter-role-worker`: в Compose он находится в профиле `promoter-roles`, а `PROMOTER_ROLE_WORKER_ENABLED` по умолчанию выключен. Он обрабатывает только уже поставленные ограниченные задания и не запускает исторический цикл. Локальный запуск после подготовки тестовой БД:

```sh
PROMOTER_ROLE_WORKER_ENABLED=true docker compose --profile promoter-roles up -d --build promoter-role-worker
```

Постановка заданий после импорта включается отдельно через `PROMOTER_ROLE_QUEUE_ENABLED=true`. Запуск профиля и включение флагов в production требуют прохождения предусмотренных спецификацией проверок; доступность профилей в конкретной конфигурации Coolify необходимо проверить при rollout.

Промежуточные роли и предложения не являются подтверждённой разметкой. Полученные через модель кандидаты не становятся RA-профилями и не используются в рекомендациях.

Для ограниченного сравнения существующего расчёта с расчётом по актуальным ролям можно выбрать конкретную пару локальных ID:

```sh
python -m app.promoter_role_shadow --artist-id ARTIST_ID --user-id USER_ID --limit 10
```

Команда выводит оба списка ID и разницу; `--persist` отдельно сохраняет два списка в `promoter_role_shadow_result`. Без этого флага результат не записывается. Если классификаций нет, shadow-выдача может быть пустой: это не оценка качества. Команда не переключает пользовательские рекомендации и не является заменой размеченному holdout.

Для ограниченного фонового shadow в recommendation-worker предусмотрены `PROMOTER_ROLE_SHADOW_ENABLED=true` и явный список внутренних user ID через запятую в `PROMOTER_ROLE_SHADOW_USER_IDS`. По умолчанию режим выключен; пустой список никого не включает. Worker сохраняет оба списка отдельно с ID задания и не меняет основной результат или кэш. При сбое shadow основной расчёт продолжает работу. Это не режим применения фильтра в пользовательской выдаче.

Подтверждение алиасов доступно только как отдельное явное решение. Сначала оператор видит исходные ID и текущую принадлежность без записи; затем может подтвердить объединение с основанием или отменить конкретное подтверждение:

```sh
python -m app.promoter_role_identity_cli --confirm ID_1 --confirm ID_2
python -m app.promoter_role_identity_cli --confirm ID_1 --confirm ID_2 --reason 'reviewed source profiles' --apply
python -m app.promoter_role_identity_cli --unconfirm ID_2 --reason 'review corrected' --apply
```

Эти команды принимают внутренние ID профилей. RA ID не меняются; каждое изменение статуса фиксируется в `promoter_identity_audit`. Профили из разных существующих идентичностей автоматически не объединяются. После изменения подтверждённых алиасов затронутые классификации становятся устаревшими и требуют повторной проверки. Не включайте фильтр рекомендаций без пересчёта и проверки кэша.
